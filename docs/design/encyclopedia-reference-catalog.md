# Encyclopedia reference catalog

Status: implemented in Glass Frontier; production reset pending.

Source reviewed: `tsonu-canon` revision `48e77f513839`, site schema version 13,
with the completed content set on 2026-08-31. `make check WORLD=glass-frontier` reports zero errors, warnings,
futures, or conversions.

The Encyclopedia is the reusable-world-material catalog beside the Atlas. It
contains organisms, cultures, ordinary roles, abilities, technologies,
resources, and recurring phenomena without turning them into named entities.

The durable distinction is:

- The Atlas contains a particular thing that can participate in history.
- The Encyclopedia contains a reusable type or pattern that may be instantiated
  in a scene.
- Chronicle history contains things established only in one play history.

An Encyclopedia entry is never a Chronicle anchor, focus candidate, named
actor, ordinary Atlas edge, or mutable lore record.

## Source state

The source implementation now exists in `tsonu-canon`. Glass Frontier consumes
the internal site bundle generated by:

```text
SITE_WORLD=glass-frontier make site-data
build/site-internal/worlds/glass-frontier.json
```

At the reviewed revision plus the authored Encyclopedia completion set, the
bundle contains:

- 283 complete, player-visible Encyclopedia records.
- Seven kinds: `lifeform`, `role`, `technology`, `resource`, `ability`,
  `phenomenon`, and `culture`.
- 21 registered context tags, all currently place-scoped.
- 204 contextual and 79 global entries.
- Five playable species and four playable cultures, all complete.
- 290 primary Atlas `type_of` classifications and 64 additional memberships.
- No duplicate slugs within either catalog and no current Atlas/Encyclopedia
  slug collision.

The current absence of a collision is not a contract guarantee.

## Ontology

| Concern | Atlas | Encyclopedia | Chronicle |
|---|---|---|---|
| Represents | One particular participant, place, object, event, or institution | A reusable type or recurring pattern | What this play established |
| Chronicle anchor | May be eligible | Never | Never a global anchor |
| Changes through play | Yes | No | Within its Chronicle |
| Relationships | Typed and often temporal graph edges | No relationship graph | Turn continuity |
| Prose storage | Lore fragments | Ordered sections on the entry | Turn record |
| Model slug | `atlas:<slug>` | `encyclopedia:<slug>` | `chronicle:<slug>` |
| Example | `atlas:blue-meridian` | `encyclopedia:flitter` | `chronicle:turn-12` |

Two tests distinguish Atlas from Encyclopedia material:

1. If independent examples can coexist, the subject may be reusable.
2. If the subject names one bounded instance whose identity persists while it
   acts, moves, changes ownership, suffers damage, or anchors a Chronicle, it
   belongs in the Atlas.

A third source-authoring test rejects generic classification labels: an entry
must name something specific to this setting about construction, operation,
stock, standing, or recurring behavior. `Flitter` qualifies. `Utility Vessel`
does not.

## Seven kinds

Glass Frontier must treat `kind` and `subkind` as opaque imported strings. The
current seven kinds answer these table questions:

| Kind | Question |
|---|---|
| `lifeform` | What lives here? |
| `role` | Who is in the room? |
| `technology` | What is this machine or engineered system? |
| `resource` | What is in the hold, store, field, or archive? |
| `ability` | What can a person deliberately do? |
| `phenomenon` | What is the world doing? |
| `culture` | Why is this learned practice, standing, or institution legible to people? |

`technology` includes vehicle classes and built infrastructure. `ability`
includes both trained techniques and extraordinary effects. `culture` includes
shared practices and the bases on which a society recognizes collective
standing. These merges are source decisions, not game code branches.

The source bundle does not export Encyclopedia kind descriptions,
classifications, field definitions, or tier definitions. Glass therefore:

- derives UI facets from the kinds and subkinds present in imported entries;
- humanizes their labels for display;
- stores facts and tier records as authored data;
- does not create kind or relationship vocabulary tables;
- does not compile the current kind list into a runtime enum.

## Source bundle contract

The source bundle uses snake_case. Glass maps it to its normal camelCase DTOs
at the import boundary.

```ts
type ContextScope = 'world' | 'place' | 'scene' | 'participant';

type ContextTagDefinition = {
  id: string;
  description: string | null;
  scopes: ContextScope[];
  parent?: string;
  compatible_with: string[];
};

type ContextTerm =
  | { scope: ContextScope; tag: string }
  | { scope: ContextScope; encyclopedia_external_key: string };

type ContextSelector = {
  all: ContextTerm[];
  any: ContextTerm[];
  none: ContextTerm[];
};

type EncyclopediaAvailability =
  | { mode: 'global' }
  | { mode: 'contextual'; selectors: ContextSelector[] };

type EncyclopediaEntrySnapshot = {
  external_key: string;
  slug: string;
  title: string;
  aliases: string[];
  kind: string;
  subkind: string;
  status: 'shell' | 'draft' | 'complete';
  dm: boolean;

  summary: string | null;
  topics: string[];
  availability: EncyclopediaAvailability | null;
  prevalence: 'common' | 'uncommon' | 'rare' | null;

  character_role: 'species' | 'culture' | null;
  origin_blurb: string | null;

  facts: Record<string, string | number>;
  descriptive_identity: Record<string, string>;
  tiers: Array<{
    tier: string;
    effect: string;
    cost?: string;
  }>;

  usage: {
    cues: string[];
    affordances: string[];
    pressures: string[];
    variations: string[];
  };

  sections: Array<{
    heading: string;
    text: string;
    audience: 'player' | 'gm';
  }>;

  instances: EncyclopediaAtlasSummary[];
  members: EncyclopediaAtlasSummary[];
};

type EncyclopediaAtlasSummary = {
  external_key: string;
  title: string;
  kind: string;
  subkind: string;
  route: string;
};

type EncyclopediaBundle = {
  entries: EncyclopediaEntrySnapshot[];
};
```

The schema retains `draft` and `shell` status shapes for future authoring, but
the authoritative Glass Frontier corpus currently contains only complete
entries. Runtime visibility still follows the status contract rather than
assuming that will remain true.

Atlas records in the same bundle add:

```ts
type EncyclopediaMembership = {
  kind: string;
  external_key: string;
};

type TsonuAtlasClassification = {
  context_tags: string[];
  encyclopedia_type: string | null;
  encyclopedia_memberships: EncyclopediaMembership[];
};
```

`encyclopedia_type` is one primary `type_of` classification.
`encyclopedia_memberships` contains additional kind-qualified memberships.
Both target Encyclopedia external keys. They are classification attributes,
not Atlas relationships.

The `instances` and `members` arrays on Encyclopedia records are derived reverse
views. Glass persists the Atlas declarations and derives reverse queries from
them; it does not create a second source of truth from the reverse arrays.

## Deliberate omissions

The Encyclopedia has:

- no relationship graph or relationship vocabulary;
- no Lore Fragments;
- no GM notes;
- no prominence;
- no Atlas `playableAs`, location, position, or route geometry;
- no temporal relationship fields;
- no mutable play state;
- no stable section identifiers.

Sections, usage, facts, descriptive identity, and tiers are replaced as parts
of their owning entry on authoritative import. They do not need independent
database identities.

## Status and visibility

The three supported statuses have different runtime treatment:

- `complete`: eligible for contextual matching, player browsing, search, and
  open.
- `draft`: eligible for player browsing and explicit search/open, visibly
  marked as draft, but excluded from proactive contextual matching.
- `shell`: retained only so Atlas classifications resolve. It is excluded from
  player and GM search, open, browsing, context matching, and Chronicle seed
  material.

Whole-entry `dm` controls entry visibility. Section `audience` controls prose
visibility inside a non-DM entry. Player APIs never return GM sections or the
GM usage arrays. The reviewed corpus currently has no DM-only whole entries and
the runtime enforces the declared contract rather than relying on that fact.

## Context tags and applicability

Three fields have separate purposes:

| Field | Meaning |
|---|---|
| `topics` | What an entry discusses; browsing and search only |
| Atlas `context_tags` | Properties contributed by a place or participant |
| `availability` | Conditions under which an entry is a useful candidate |

The game never treats a topic as an applicability tag.

An entry is applicable when it is complete and either global or at least one
selector matches. Within a selector:

- every `all` term must match;
- one `any` term must match unless `any` is empty;
- no `none` term may match.

Selectors are alternatives. A selector match means the entry is useful here,
not that an instance is present or that other inventions are forbidden.

The implementation supports all four declared scopes and Encyclopedia identity
terms without branching on the initial corpus. The current content uses only
place-scoped tag terms. Initial scene profiles therefore begin with the current
Atlas location's imported context tags; future source content can add other
declared scopes without changing the persisted entry shape.

Primary types and memberships are not availability edges. They answer what a
particular Atlas record instantiates or belongs to. A complete classification
target may be supplied as directly relevant context when that Atlas record is
already relevant to the turn.

## Species and culture

Species and cultures belong in the Encyclopedia. They are reusable bodily and
learned contexts, not actors.

Character origin crosses the catalogs explicitly:

```ts
type CharacterOrigin = {
  speciesReferenceId: string;
  cultureReferenceId: string;
  homelandId: string;
  allegianceId: string;
  allegianceStance: AllegianceStance;
};
```

The database may use internal UUIDs for referential storage. Model prompts and
retrieval tools never receive them. Character prompts resolve all four values
to names and usable prose before model invocation.

Only complete, non-DM entries with the corresponding `character_role` are
selectable. The source currently supplies five species and four cultures, all
with `origin_blurb`.

## Context browser and player references

Applicable Encyclopedia material uses one reusable player-facing browser. It is
mounted as `Common here` during Chronicle creation and in the Chronicle left
rail below the named Atlas items during play.

The browser groups a flat applicable-entry response into a tree:

1. kind;
2. rarity, sourced from the entry's `prevalence` field;
3. entry.

Kind and rarity branches expand and collapse independently. Rarity groups sort
`common`, `uncommon`, then `rare`, and entries sort by title. Reuse belongs in
the client component and its interaction model; the API continues to return
ordinary qualified-slug summaries rather than a presentation-specific tree.

A single click opens the entry in the shared Atlas/Encyclopedia World Guide
modal. During play, double-click or right-click attaches the entry to the
pending player message as a direct reference. Chronicle creation uses the same
browser without attachment gestures.

The World Guide modal generalizes the existing `AtlasModal`: its state carries
one qualified slug and dispatches to the owning Atlas or Encyclopedia detail
surface. Atlas and Encyclopedia do not maintain competing global modals.

Player-message references cross the catalog boundary by qualified slug. The
composer holds one list containing values such as `atlas:blue-meridian` and
`encyclopedia:flitter`, renders them as removable chips, and submits them beside
the player's prose. The server resolves each slug only in its declared store.
An Encyclopedia attachment supplies intentional context to the GM and can
produce reference usage, but it never becomes entity focus or an Atlas graph
event.

The live browser refreshes from the Chronicle's canonical location context and
shows every complete, player-safe match returned for that context. Hidden GM
candidates, match evidence, and private usage remain server-side. As with every
applicability result, the tree is suggestive rather than exhaustive.

## GM retrieval contract

The GM receives two tools: `search` and `open`.

```ts
search({ query: string })
open({ slug: string })
```

Both tools span Atlas, Encyclopedia, and Chronicle history. No model-facing
request or result contains a database UUID, opaque handle, or separate source
field.

Search always returns a fully qualified slug in its `slug` field:

```ts
type SearchResult = {
  slug: string; // atlas:blue-meridian, encyclopedia:flitter, chronicle:turn-12
  title: string;
  kind: string;
  excerpt: string;
};
```

The model copies `slug` directly into `open`.

`open` resolves slugs as follows:

1. A qualified slug searches only its named store and never falls back.
2. A bare slug searches all three stores for an exact slug.
3. One bare match opens normally.
4. Multiple bare matches return an ambiguity error containing the qualified
   alternatives.
5. No match is a retrieval miss, not a statement that the fiction cannot
   exist.

The seed `WORLD-INDEX` uses the same fully qualified slugs. Atlas lore search
results return the owning Atlas entity's qualified slug, so the result opens
through the ordinary Atlas record rather than requiring a lore-specific tool.
Chronicle results use readable slugs such as `chronicle:turn-12`.

The single `search` replaces separate entity, lore, Encyclopedia, and Chronicle
search tools. The single `open` replaces source-specific read tools. Opening an
Atlas record supplies relevant lore and related qualified slugs; opening an
Encyclopedia record supplies its complete GM view; opening a Chronicle record
supplies the established turn evidence.

Tool-session provenance is keyed by qualified slug. Entity sidecars and
Encyclopedia usage sidecars remain semantically separate even though discovery
is shared.

## Open-world invention

- A match means the material is useful here.
- No match says nothing about what is possible.
- Absence never forbids player or GM invention.
- A matched entry is not proof that an instance is present.
- New common material remains Chronicle history unless a GM or editor promotes
  it through `tsonu-canon`.
- A new particular can become a Chronicle-local actor without changing its
  reusable type into an actor.

Actual Encyclopedia use is recorded separately from entity focus:

```ts
type TurnReferenceUsage = {
  slug: string; // encyclopedia:<slug>
  role: 'texture' | 'interaction' | 'character_origin' | 'instance_basis';
};
```

The model-facing sidecar and the durable turn record both name the entry by its
qualified slug. Internal database UUIDs are confined to persistence joins and
character-origin columns.

## Source integration finding

The remaining source boundary is guide content. General guide pages, including
`Life in the System`, are emitted only in the public site tree, not the internal
single-file bundle used by the Glass importer. Guide ingestion remains outside
this cutover unless Tsonu adds those pages to the internal artifact or Glass
deliberately consumes the public page tree as a second input.

Draft and shell handling remains part of the schema contract, but neither
status exists in the current content and neither changes the integration path.
